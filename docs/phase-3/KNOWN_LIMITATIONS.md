# Known limitations

- The repository/log analysis engine is deterministic and vendor-neutral. It implements structured analysis and safety boundaries but is not connected to a hosted LLM. A production provider adapter should use structured outputs and the same redaction boundary.
- Local application builds and runtime containers are real (a real `git clone` + sandboxed `docker build` + labeled `docker run` + `cloudflared` tunnel) for a project with a connected GitHub repository and Node/Bun/Docker-runtime services — including rollbacks and template-marketplace deploys. Builds drop capabilities, disable privilege escalation, pin CPU/RAM/PIDs, and refuse to run an image whose sha256 digest does not match the HMAC signature stored at build time. `apps/build-worker` is the dedicated multi-node builder (BullMQ `builds` queue). Isolation is Docker's, not a hardware hypervisor. Projects without a connected repo, or with an unsupported runtime, still use the simulation adapter.
- MySQL/MariaDB provisioning is fully implemented locally (`MysqlAdminService`). MongoDB provisioning is implemented the same way (`MongoAdminService` against `mongo:7` with auth on, port 27018). MariaDB currently shares the MySQL 8.4 server rather than a genuinely separate MariaDB instance.
- API-key rate limiting is Redis-backed and shared across every API process (see `AnyAuthGuard`). Other cross-process coordination (locks, leader election for schedulers) hasn't had the same HA review yet.
- Traefik configuration is written only when `TRAEFIK_DYNAMIC_CONFIG_PATH` is configured; dynamic provider reload and edge deployment remain operator responsibilities.
- Custom domain verification (`DomainsService.verify`) performs real DNS resolution of the TXT ownership token and the apex A record and fails closed if either doesn't match yet. After a match, `SslIssuanceService` writes a Traefik file-provider router with `tls.certResolver=letsencrypt` and polls Traefik until the router reports TLS. SSL is `ACTIVE` only when Traefik has a certificate; otherwise it stays `ISSUING` with `lastError`. Let's Encrypt HTTP-01 requires port 80 on `PLATFORM_INGRESS_IP` (`TRAEFIK_HTTP_PORT=80` in production).
- SSO/SAML, SCIM, organization IP allowlists, dedicated nodes/databases, private networking, SLA, custom retention, and audit export are modeled as enterprise architecture but are not complete customer-facing products. (Encryption-key rotation is complete — see LAUNCH_READINESS.md.)
- Client portal permissions and white-label settings are modeled and administered, but a separately hosted custom-domain client portal/login experience is future work.
- CPU/RAM/request autoscaling depends on recent service metrics. Production agents must supply trusted metrics and request-rate telemetry.
- Outbound network/process abuse signals are collected for real and turned into actionable `RiskEvent` records by `apps/runtime-agent`. Real app containers are labeled `com.clouddeploy.container-id=<platform Container.id>` at start, so live deploy traffic is visible to the agent. BRUTE_FORCE/SPAM/MALWARE/PHISHING still need application-log/content signals this agent does not collect.
- The public status page is implemented at `/status`; serving it from `status.clouddeploy.app` requires DNS and edge routing configuration.
- Template definitions can describe volumes and health checks, but production enforcement depends on the runtime provider.
- Fixed: `packages/database/prisma/seed.ts` used to re-create the `shopfront` project's services, deployment, `shopfront-db` Database row, and environment variables on every `npm run seed` run instead of upserting them, and encrypted the seeded database password and env var secrets with a non-`encv1:` placeholder string that could never actually decrypt. Both are now idempotent (find-or-create/upsert) and encrypted with the real `ENCRYPTION_KEY` (read from `packages/database/.env`, which must match `apps/api/.env`'s value for the seeded secrets to decrypt through the running API). The seed script also now provisions `shopfront_user`/`shopfront` for real on the local Postgres server (same primitives as `PostgresAdminService`) with sample `users`/`orders` tables, so the demo project's connection details, live metrics, table browser, and SQL editor all work out of the box instead of pointing at a role that doesn't exist. A long-lived local database seeded before this fix will still have the old duplicate/undecryptable rows sitting around; only a fresh `prisma migrate reset && npm run seed` clears those out.
